# 第五章：网格单元与阵纹解析

## 1. 两种网格载体

当前存在独立网格面板和阵总线网格面处理器两种载体。两者都使用 4×4 单元格存储，但它们不是已经完整闭环的正式绘阵系统。

独立网格面板是厚度 1/16 的水平薄片；阵总线中的网格处理器可位于任意表面，并按表面方向把点击坐标转换为二维格坐标。

## 2. 编辑操作

编辑时主手必须持木棍：

- 副手持有效动作对应物品，主手木棍点击目标格，将该动作写入单元格。
- 副手为空，主手木棍点击目标格，清除该单元格。

当前动作映射如下：

| 副手物品 | 动作 | 元素 |
| --- | --- | --- |
| 烈焰粉 | fire | 火 |
| 水桶 | water | 水 |
| 泥土 | earth | 土 |
| 羽毛 | wind | 风 |

`empty` 动作使用空气注册，但副手为空执行的是清除，不是主动写入该动作。

## 3. 解析触发条件

阵总线网格处理器只在 4×4 全部填满且本轮尚未触发解析时运行规则。它遍历注册规则，执行第一个匹配项。网格快照和触发状态会持久化。

当前唯一内置规则名为 `unstable_sift_zhen`，匹配器由 2×2 全土图案和 `SHARP` 模式构造，方向参数为 5。源码注释和实际构造参数存在不一致，因此应以构造代码为准，不应照搬旧注释中的“4×4 全火”。

## 4. 当前规则的实际结果

该规则匹配后，处理器只记录一条日志：报告规则在某位置匹配。规则处理函数没有替换方块、安装筛分阵、消耗材料或给予物品。

因此当前网格系统应标记为**受限实现/开发骨架**：

1. 单元格编辑和保存已经存在。
2. 4×4 填满触发已经存在。
3. 注册表驱动的图案匹配已经存在。
4. 唯一内置规则的业务结果仍是占位日志。

## 5. 验证路线

1. 放置独立网格面板，确认主手木棍、副手四种材料能编辑对应格。
2. 清空副手后点击，确认单格被清除。
3. 若验证总线网格处理器，需要先确保目标面确实安装的是 `grid_cell` 类型；当前普通玩家入口并未提供完整、明确的安装流程。
4. 填满 4×4 后观察服务端日志，确认解析只触发一次。
5. 修改网格后重新验证触发标记是否按预期重置；不要假设重复填满一定重复执行。

## 6. 使用限制

- 独立网格面板本身的服务端 tick 与总线网格处理器不是同一实现路径，不能默认两者拥有完全相同的规则触发效果。
- 当前没有完整中文提示告诉玩家某格坐标、动作或匹配结果。
- 当前图案规则数量只有一个，且处理逻辑为占位。
- 当前教程不把网格描述为合成阵方块的正式生存玩法。
- 后续扩展规则时必须明确图案尺寸、方向、匹配模式、材料映射和触发后果，避免仅靠注释表达协议。
