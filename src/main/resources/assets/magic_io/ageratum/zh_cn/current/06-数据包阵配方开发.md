# 第六章：数据包阵配方开发

## 1. 文件位置与加载

内置配方位于 `data/magic_io/recipe/<等级目录>/`。加载器从资源管理器读取 JSON，解析后放入独立的阵配方管理器，并通过网络负载同步给客户端。数据重载时配方会重新建立。

配方文件中的 `type` 当前示例统一写作 `magic_io:zhen_block`，但自定义加载器的核心字段是 `zhen_type`、输入、输出和 `processing_time`。

## 2. 最小物品配方

```json
{
  "type": "magic_io:zhen_block",
  "zhen_type": "magic_io:unstable_cinder_zhen",
  "inputs": {
    "item_input_all": [
      {"item": "minecraft:coal", "count": 1}
    ]
  },
  "outputs": {
    "item_output_all": [
      {"item": "magic_io:coal_coke", "count": 1}
    ]
  },
  "processing_time": 100
}
```

`count` 缺省时为 1。`item` 使用当前 Minecraft/NeoForge 的标准 Ingredient 格式，数量由外层需求独立保存，不会展开成重复条目。

## 3. 区域名称

普通阵应使用现有区域名：

- `item_input_all`：物品输入。
- `item_output_all`：物品输出。
- `fluid_input_all`：流体输入，前提是阵类型具有对应流体槽。
- `fluid_output_all`：流体输出。
- `drop_output`：世界掉落输出。

区域名必须和目标阵类型的槽位分区匹配。JSON 能被解析不代表目标阵有可用槽位；例如给纯物品阵添加流体输出，不会自动创造流体槽。

## 4. 流体格式

```json
{
  "type": "magic_io:zhen_block",
  "zhen_type": "magic_io:unstable_dew_zhen",
  "processing_time": 10,
  "fluid_outputs": {
    "fluid_output_all": [
      {"fluid": "minecraft:water", "amount": 20}
    ]
  }
}
```

流体输入写在 `fluid_inputs`，流体输出写在 `fluid_outputs`。输入流体字符串支持直接 ID，也支持以 `#` 开头的流体标签；输出必须解析为具体流体。数量单位沿用 NeoForge 流体栈语义。

**限制：**当前流体消耗路径存在未完整实现的通用 `consume` 方法，扩展带流体输入的生产配方前必须进行实际消耗测试，不能仅凭加载成功认定无复制问题。

## 5. 战利品表输出

可在某个物品输出区域内写：

```json
{"loot_table": "magic_io:sift_metal_drop"}
```

战利品表输出必须写在明确的输出区域中。服务端实际执行时才会抽取结果；JEI 只能通过解析本地资源尽量展示候选项，并不能代替服务端实际抽取结果。

## 6. 等级继承设计

配方的 `zhen_type` 指向其最低目标等级。实际阵等级更高且基础功能相同时，管理器可找到低等级配方并应用累计倍率。推荐不要为每个高等级复制完全相同的 JSON；只在材料、结果或基础时长确实变化时增加新等级配方。

## 7. 错误处理与验证

- 未知阵类型会导致该 JSON 加载失败并记录警告。
- 缺失 `processing_time`、非法 ID 或错误 JSON 结构会使配方返回空并被跳过。
- 不存在的物品可能被跳过，导致输入或输出列表与作者预期不同。
- 输出区域满时配方不会正常完成，应同时验证满仓行为。
- 数据重载后要同时验证服务端配方、客户端 JEI 和实际加工，三者任一成功都不能单独证明完整同步。

推荐验证顺序：先复制一个当前有效的最小配方，只改文件 ID和目标阵；再改输入；再改输出；最后加入流体或战利品表。每一步都用单次材料和满仓两种场景测试。
