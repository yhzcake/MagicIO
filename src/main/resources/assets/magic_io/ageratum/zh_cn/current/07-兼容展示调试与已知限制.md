# 第七章：兼容展示、调试与已知限制

## 1. JEI 兼容

当前提供 JEI 模组插件服务入口和阵配方分类。JEI 用于展示阵配方，并对战利品表候选产物增加“±随机”提示。

构建脚本只声明 JEI API 为 `compileOnly`，完整 JEI 运行时依赖处于注释状态。因此：

- 发布模组不强制要求 JEI。
- 本地没有安装 JEI 时，不应期待配方页面出现。
- 教程不建议自动修改构建依赖；需要 JEI 调试时应由开发者明确决定运行时安装方式。
- 战利品表解析是展示辅助，不保证完整复现所有复杂原版战利品条件和函数。

## 2. Jade 兼容

Jade 同样是编译期可选依赖。安装后可针对阵总线显示：

- 当前命中面的阵名称。
- 该面处理器的物品信息。
- 流体信息。
- 能量当前值与容量。

Jade 的面识别复用阵总线视线检测。若边缘瞄准显示了错误处理器，应换一个更靠近面中心的视角复测，再判断是否为数据错误。

## 3. 客户端标签导出命令

进入世界后可执行：

```text
/magicio tags
```

该客户端命令遍历当前物品注册表中的非空标签，按命名空间和标签路径排序，输出到游戏目录下：

```text
magicio/tags-<时间戳>.json
```

它只导出物品标签，不导出流体标签、方块标签或阵配方。命令必须在已进入世界且客户端注册表可用时执行。

## 4. 传送门功能

古朴传送门阵是当前少数具有专属 tick 行为的功能。它每 tick 检查阵方块范围内的服务端玩家；玩家主手必须持示例物品，自定义数据中必须有合法 `position` 字符串，并且玩家正在潜行。

接受的格式为：

```text
x,y,z
x,y,z yaw pitch
```

yaw 必须严格位于 -180 到 180 之间，pitch 必须严格位于 -90 到 90 之间。当前实现传送到同一 `ServerLevel`，没有维度 ID 参数。

**限制：**当前没有正常玩家交互负责把 `position` 写入示例物品；已有右击空气逻辑会重建自定义数据并只保存 `side`，可能覆盖其他字段。因此传送门应视为开发级接口，而非闭环生存功能。

## 5. 配置与示例残留

当前公共配置只有记录泥土方块、魔法数字、魔法数字介绍文本和待记录物品列表，均沿用模板示例性质。它们不控制阵速度、产出、能耗或总线容量。不要向整合包作者宣称这些配置可以平衡核心系统。

中文语言文件仍包含示例方块和示例物品名称；创造标签页图标也是示例物品。项目存在 `ExampleMixin` 与其他开发命名，不能据此推导正式玩法。

## 6. 系统性排错路线

1. **确认类型**：记录实际阵方块或总线目标面的完整注册 ID。
2. **确认数据**：检查配方 `zhen_type`、区域名、输入 ID、输出 ID 和处理时长。
3. **确认存储**：保证输入进入正确槽，输出槽或流体槽有空间。
4. **确认等级**：高等级可向下兼容，同功能低等级不能处理高等级配方。
5. **确认加载**：保持区块加载，重载数据后观察服务端警告。
6. **确认展示边界**：JEI/Jade 缺失只影响辅助信息，不等价于核心配方缺失。
7. **确认随机输出**：同时检查普通输出槽和阵附近的物品实体。

## 7. 当前已知限制总表

| 模块 | 限制 |
| --- | --- |
| 生存流程 | 缺少取得全部阵与总线的完整合成链 |
| 阵功能 | 多数仅由 JSON 区分，没有专属机制 |
| 能量 | 有 IO 框架，但当前核心配方未形成明确 FE 消耗闭环 |
| 流体输入 | 消耗路径需要额外运行验证 |
| 网格 | 唯一内置解析规则只记录日志 |
| 传送门 | 依赖无法由正常流程稳定配置的示例物品数据 |
| 创造阵 | 无输入生成命令方块，属于占位内容 |
| 配置 | 仍是模板示例，不控制核心平衡 |
| 可选兼容 | JEI/Jade 不随核心依赖强制提供 |

## 8. 结论

当前源码已经形成可扩展的阵类型注册、等级继承、物品/流体 IO、数据驱动配方、阵总线多面处理和客户端配方同步骨架。最适合的使用方式是创造模式机制验证与数据包原型开发。若要作为正式生存模组发布，仍需补齐获取链、正式交互、网格业务结果、能源语义、流体输入验证、配置项和整体平衡。
