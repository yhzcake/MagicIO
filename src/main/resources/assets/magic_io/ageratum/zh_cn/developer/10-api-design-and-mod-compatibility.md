# 第 10 章：API 设计与模组兼容

MagicIO 当前没有单独发布的 `api` 源集或稳定 API 工件，但源码已经提供多个可扩展注册点：自定义注册表、阵功能描述、IO 抽象、配方修饰器、网格动作与解析规则。本章区分“现有可用扩展点”和“尚未承诺稳定的内部实现”。

## 1. 兼容层级

扩展优先级建议如下：

1. **数据包**：配方、战利品表和标签，不产生 Java 硬依赖。
2. **注册表扩展**：通过 NeoForge 模组事件总线注册 `ZhenType`、`IOType` 等对象。
3. **行为扩展**：注册 `RecipeModifier`、`GridParseRule` 或自定义处理逻辑。
4. **可选模组适配器**：在独立 compat 包中调用第三方 API。
5. **Mixin 或内部反射**：仅在没有公共扩展点时使用，并接受最高维护成本。

能用数据解决的问题不要优先写 Java 兼容层。数据 ID 比内部类名稳定，也更容易由整合包覆盖。

## 2. 自定义注册表

项目通过 `NewRegistryEvent` 建立多个自定义注册表：

- `magic_io:element_type`：元素类型。
- `magic_io:zhen_type`：具体阵类型。
- `magic_io:io_type`：资源 IO 类型。
- `magic_io:cell_action`：网格单元动作。
- `magic_io:grid_parse_rule`：网格解析规则。

内置对象使用 `DeferredRegister` 注册。第三方扩展也应在自己的模组构造阶段，把 DeferredRegister 绑定到自己的模组事件总线，避免直接修改注册表或在注册冻结后写入。

注册对象的命名空间应属于扩展模组。例如第三方阵类型应使用 `other_mod:...`，不要占用 `magic_io` 命名空间。跨模组引用通过 `Identifier` 或注册表 Holder 完成，避免依赖具体静态字段。

## 3. 阵功能与阵类型

`ZhenFunction` 是批量生成等级化阵类型的内部便利描述：它记录基础名、元素、首次出现等级、槽位分区、面访问、tick 工厂和流体容量。调用 `register` 时会遍历 `ZhenLevel.ALL`，为可用等级生成：

```text
<level_prefix><base_name>_zhen
```

`ZhenType` 才是进入注册表的最终对象。设计第三方阵时需要同时确定：

- 稳定的基础名与完整注册 ID。
- 属于哪个元素类型。
- 从哪个等级开始可用。
- 每种 `IOType` 的槽位区域。
- 六个方向各自暴露哪些区域。
- 是否有每 tick 行为。
- 流体或能源容量。
- 是否沿用 `RecipeProcessor` 的数据配方流程。

基础名会参与配方缓存与 JEI 类别归组。随意改名会同时破坏配方查找、已有数据包和显示集成。

## 4. IO 扩展

当前内置 `IOType` 包括物品、流体和能源。`IOProcessor` 按类型保存 `IOComponent<R,T>`，配方输入输出也用 `RecipeInput<?>`、`RecipeOutput<?>` 携带类型与区域。

新增资源类型不仅是注册一个 `IOType`，还需要完整实现：

1. 资源需求和输出值的数据模型。
2. 对应 `IOComponent` 的查询、模拟、消耗、生产与持久化。
3. `SlotPartition` 中该类型的区域布局。
4. 方位访问映射。
5. 配方 JSON 解析。
6. MapCodec 与 StreamCodec。
7. `RecipeProcessor` 的匹配、预检、消耗和产出。
8. JEI/Jade 或其他界面展示。

只注册 `IOType` 而不补齐链路，会得到“注册成功但无法参与配方”的空壳类型。

NeoForge 26.1 当前源码使用 Transfer API 的 `ResourceHandler`、资源对象与事务上下文。不要直接套用旧版 Forge Capability 的 `IItemHandler`/`LazyOptional` 架构，除非专门编写桥接层。

## 5. 配方修饰器

`RecipeModifiers.register(RecipeModifier)` 是较轻量的行为扩展点。所有修饰器按注册顺序遍历，时间倍率和产出倍率分别乘法叠加。

兼容实现应遵守：

- 判断目标阵类型或配方后再修改，不要无条件影响全部配方。
- 返回值必须可预测并有合理上下限。
- 不在每 tick 计算中执行昂贵注册表扫描。
- 多个模组同时注册时不依赖固定顺序，除非 API 明确提供优先级。
- 服务器决定最终倍率，客户端显示只能作为提示。

当前 `RecipeModifiers` 是普通静态列表，不是 NeoForge 注册表，也没有重复注册保护或稳定排序协议。因此它适合作为源码级扩展点，但还不应被宣传为跨版本稳定 API。

## 6. 网格动作与解析规则

`CellAction` 描述网格单元可识别的动作，`GridParseRule` 则组合匹配条件、目标阵类型和处理器。规则按注册顺序遍历，并执行第一个匹配项。

第三方规则需要注意冲突：

- 匹配条件越宽泛，越可能抢先截获其他规则。
- 注册顺序跨模组时不应被视为稳定业务优先级。
- 规则处理器应验证输入上下文，不要假定网格一定完整或对象一定属于本模组。
- 若两个模组声明相同图案，应通过配置、明确优先级 API 或更具体模式解决，而不是依赖偶然加载顺序。

## 7. 数据兼容的当前限制

虽然数据驱动是首选，但当前阵配方扫描器限制资源命名空间为 `magic_io`。这意味着第三方模组无法仅在自己的 `data/other_mod/recipe` 下添加阵配方并被现有加载器发现。

现阶段可选路线需要明确权衡：

- 整合包把兼容配方放进 `magic_io` 命名空间：实现简单，但存在资源 ID 覆盖和所有权不清晰问题。
- 扩展加载器允许多个命名空间：架构更合理，但属于核心代码演进。
- 提供正式配方注册事件或 API：适合 Java 扩展，但必须处理重载生命周期和网络同步。

在正式 API 出现前，不应承诺第三方命名空间阵配方已经原生可用。

## 8. 可选依赖模式

JEI/Jade 已展示推荐模式：

- 构建期使用 `compileOnly` API。
- 模组元数据使用 `type="optional"`。
- 适配代码放在独立 compat 包。
- 通过对方规定的服务发现或插件入口加载。
- 核心类签名不暴露可选依赖类型。

对其他模组做兼容时，还应先检测其是否加载，再进入兼容初始化。不要通过捕获 `ClassNotFoundException` 掩盖结构性类加载问题。

## 9. API 稳定性建议

如果计划把 MagicIO 作为其他模组的开发依赖，建议后续建立明确边界：

1. 新建独立 API 包，只暴露接口、注册键、事件和不可变数据对象。
2. 使用语义化版本记录破坏性变更。
3. 避免 API 返回内部可变集合或单例缓存本体。
4. 为注册阶段、服务端重载阶段和客户端同步阶段提供明确事件。
5. 为配方扩展提供统一 Codec，消除手工 Gson 与 MapCodec 的能力差异。
6. 给网络协议建立版本策略或由 NeoForge 版本协商阻止不兼容连接。
7. 为 JEI/Jade 建立只依赖公开视图模型的适配层。

## 10. 兼容性测试矩阵

每个扩展至少验证：

| 场景 | 检查重点 |
| --- | --- |
| 仅 MagicIO | 核心注册、配方执行、重载正常 |
| MagicIO + 扩展模组 | 注册 ID、配方、倍率和规则正常 |
| 缺少可选前置 | 核心模组不发生类加载错误 |
| 单人游戏 | 集成服务器同步到本地客户端 |
| 专用服务器 | 不加载客户端 API，服务端权威执行 |
| `/reload` | 缓存替换、战利品表更新、客户端刷新 |
| 玩家中途加入 | 收到完整配方快照 |
| 多扩展共存 | 注册表、规则顺序和倍率叠加无冲突 |

## 11. 故障定位

- **注册对象不存在**：检查 DeferredRegister 是否绑定正确事件总线、注册键是否一致。
- **配方找不到第三方阵**：检查 `zhen_type` 注册时机、基础名规则和扫描命名空间限制。
- **自定义 IO 不执行**：逐项核对解析、网络、分区、组件和处理器链路。
- **只在重载后失效**：检查静态扩展列表是否被清空后重新注册，以及缓存替换时序。
- **客户端显示与服务端不同**：以服务端为权威，检查完整快照同步和展示解析限制。
- **缺少可选模组时崩溃**：检查核心类静态引用、公共方法签名和服务入口隔离。

## 12. 开发原则总结

MagicIO 的兼容开发应围绕稳定资源 ID、服务端权威、注册阶段安全和可选依赖隔离展开。现有自定义注册表提供了良好扩展基础，但静态配方缓存、手工 JSON 加载器和部分内部便利类尚未形成正式稳定 API。第三方扩展应明确绑定目标 MagicIO 版本，并在升级 NeoForge、Minecraft 或 MagicIO 后重新验证完整测试矩阵。
